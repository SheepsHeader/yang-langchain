## 一、核心心智模型（费曼式）

一条记忆存进去，其实是 **三个东西**：

```
namespace（抽屉）  →  ("my-user", "chitchat")     放哪个抽屉
key（卡片名字）     →  "a-memory"                  这张卡叫什么
value（卡片内容）   →  {"rules": [...], "topic": "language"}   卡片上写的字
```

- **namespace 分层**：第 0 层"是谁的"（用户），第 1 层"哪个场景"（闲聊），还可以继续叠
- **同一个 agent 对同一个用户**：通常是同一 namespace 下挂很多 key 不同的记忆（偏好、事实、摘要……）
- **同 namespace + 同 key 再 put = 覆盖更新**，不是新增

## 二、三个操作速查

| 我想干嘛 | 用什么 | 依据 |
|---|---|---|
| 按名字精确拿一条 | `get(namespace, "a-memory")` | **key**（唯一看 key 的操作） |
| 按意思模糊找相关 | `search(namespace, query="...")` | **整个 value 的内容**（嵌入比相似度） |
| 在结果里缩小范围（可选） | `search(..., filter={"topic": "language"})` | **value 里字段的精确相等** |

**一句话：key 是"点名"用的（get），query 是"凭意思找"用的，filter 是"看标签"用的。query 是主力，filter 是可选。**

---

## 三、search 内部的两阶段过程

```
全部记忆（namespace 内）
   │
   ▼ ① filter 划门槛 —— 只查 value 的字段（精确相等，不看 key）
   ├── a-memory (topic=language)   ✓ 入围
   ├── b-memory (topic=travel)     ✗ 出局
   └── c-memory (topic=language)   ✓ 入围
   │
   ▼ ② query 语义排序 —— 整个 value 嵌入成向量，对入围者算相似度
   按 score 从高到低返回（默认最多 10 条）
```

- `filter` 决定 **候选人是谁**；`query` 决定 **候选人里谁最相关**
- 嵌入覆盖**整个 value**（rules + topic 都算），所以语义相关的"真数据"在 rules 里也能被 query 读到

## 四、误区纠正表（本笔记最有价值的部分）

| # | 我当时以为 | 正确理解 |
|---|---|---|
| 1 | filter 过滤的是记忆的 key（a-memory、b-memory 这类名字） | filter **根本看不到 key**，它只查 value 内部字段。get() 才用 key |
| 2 | filter 里的键值对是从 value 里"拿出来"的 | filter 本来就是去 value 内部字段做**精确相等匹配**，是它的设计职责 |
| 3 | filter 是两步：先按 topic 过滤，再筛值等于 language | 一个键值对 = **一个整体条件**：`topic` 字段恰好等于 `"language"`。多个键值对才是多个"且"条件 |
| 4 | query 是 "language preferences"，但真数据在 rules 里，会不会查不到 | 不会。query 嵌入的是**整个 value**（含 rules），filter 只是划门槛不参与语义比对；**去掉 filter 也能查到** |
| 5 | `filter={"rules": "language"}` 会在 rules 列表里找含 "language" 的 | filter 是**字段整体精确相等（标量）**，列表 ≠ 字符串 → 恒 False → 返回 `[]`。想在内容里找得用 `query` |
| 6 | 搜索要提前知道记忆里的键值对，很复杂 | filter **可选**。只用 `query` 什么都不用知道；filter 要的字段是你**自己起的标签**，不会不知道自己贴了什么 |
| 7 | 占位 `embed` 能真正按意思搜索 | 占位函数让所有文本向量相同，search 的 score 恒 1.0，**没有语义区分度**。换真实嵌入模型才有真语义搜索 |
| 8 | 把 topic 改成 "language lll" 后，原 filter 还能搜到 | 精确相等不成立 → 返回 `[]`。需同步改 filter；且整个 value 会重新嵌入，向量也变了 |

## 五、真实的语义搜索：换掉占位 embed 之后

```python
from langchain.embeddings import init_embeddings
store = InMemoryStore(index={
    "embed": init_embeddings("openai:text-embedding-3-small"),
    "dims": 1536,
})
```

### 过程（3 步）

1. **put**：整个 value 序列化 → 嵌入 → 1536 维向量，与原数据一起存进内存（1 次嵌入调用）
2. **get**：零计算，纯按 namespace+key 原样取回
3. **search**：filter 精确筛 → query 也嵌入成向量 → 对入围者算**余弦相似度**（归一化到 0~1）→ 排序取 Top

### 输出示例

```python
[SearchItem(namespace=('my-user', 'chitchat'), key='a-memory',
            value={'rules': [...], 'topic': 'language'},
            score=0.63)]
```

`score` 越高越相关；存 1 条记忆时看不出排序威力，**存几十条才能体现** query 从一堆里挑最相关的。

### 占位版 vs 真实版

| | 占位 embed | 真实模型 |
|---|---|---|
| 每条记忆的向量 | 全一样 | 独一无二 |
| search 的 score | 恒 1.0（等于没排） | 有高有低，真实反映相关性 |
| 嵌入调用 | 无实际调用 | put 1 次 + search 1 次 |

## 六、关键边界与生产注意

- **InMemoryStore = 数据在内存**，进程退出即丢，只适合开发测试
- **生产用数据库存储**：`PostgresStore`（PostgreSQL + 向量搜索，重启不丢）、Redis 等
- **语义搜索默认关闭**：不配 `index`（embed + dims），`search` 的 `query` 参数无效
- **filter 只支持标量精确相等**：不支持大于/小于/模糊；复杂条件靠 namespace 分层 + query 语义去凑
- **key 可以不取名字**：塞个 UUID 也行，找记忆全靠 query
- 占位 `embed` 还有个 bug 隐患：`[1.0, 2.0] * len(texts)` 生成的数字个数和声明的 `dims: 2` 对不上

## 七、一句话总结

> **namespace 是抽屉，key 是卡片名，value 是卡片内容；
> get 点名、query 凭意思找、filter 按标签筛；
